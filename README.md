## Запуск у себя через Docker

Нужен Docker и Node.js. Node нужен только для `npm install` и сборки web-образа; без него сборка идёт обычными командами docker.

1. Распакуйте архив релиза (zip или tar.gz) в любую папку.
2. Скопируйте `.env.example` в `.env` и заполните ключи и логин PocketBase. Без `.env` запуск не начнётся.
3. Запустите контейнеры:

   - Windows: `docker-up.bat`
   - Linux и macOS: `docker compose up -d`

Флаги `docker-up.bat`:

- `--skip-sync` — поднять только web и PocketBase, без фоновых скраперов (в `docker-compose.yml` 7 сервисов, из них 5 фоновые);
- `--recreate` — пересоздать контейнеры;
- `--skip-build` — не пересобирать web-образ;
- `--superuser` — создать superuser PocketBase из `PB_EMAIL` и `PB_PASSWORD` в `.env`.

После запуска: приложение на `http://localhost:3000`, PocketBase на `http://localhost:8090`. Миграции из `pb_migrations` применяются при первом старте контейнера с базой.

lib

static

- static/\* - favicon.svg и robots.txt

- static/icons - иконки
- static/images - картинки

## Релизы (/releases)

Плитки релизов строятся из коллекции `releases` в PocketBase (миграция
`pb_migrations/1730000200_created_releases.js`). У kg-portal нет публичного API и CORS,
поэтому данные собираются серверным скриптом и сохраняются в базу.

```bash
# только парсинг, ничего не записывается и не вызывается API
npm run scrape:releases -- --dry-run --no-api --weeks 2

# парсинг + подбор kinopoiskId + запись в PocketBase
PB_EMAIL="admin@example.com" PB_PASSWORD="password" npm run scrape:releases -- --from 2026-01-01 --weeks 40
```

Флаги:

- `--from YYYY-MM-DD` — дата, от которой считаются недели (всегда понедельник), по умолчанию текущая
- `--weeks N` — сколько недель парсить (1–20)
- `--delay MS` — пауза между запросами к kg-portal, по умолчанию 1200
- `--no-api` — не обращаться к Kinopoisk API, поле `kinopoiskId` остаётся пустым
- `--limit N` — максимум записей
- `--dry-run` — вывод в консоль без записи

Плитка ссылается на страницу фильма (`/watch?id=...`), поэтому `kinopoiskId` обязателен:
без него плитка показывается, но не кликается. Запись обновляется по полю `slug`,
уже решённые `kinopoiskId` повторно не запрашиваются.

Страница `/releases` показывает неделю (пн–вс), стрелки листают недели назад и вперёд,
`?week=YYYY-MM-DD` можно передать в URL.

### Календарь аниме (вкладка «Аниме»)

Тот же блок с переключателем: слева — фильмы (коллекция `releases`), справа — аниме
(коллекция `anime_releases`, миграция `pb_migrations/1730000300_created_anime_releases.js`,
применится при следующем запуске PocketBase). Вкладка в URL: `?type=anime`. Аниме показывается не больше чем в 2 ряда (сколько плиток в
ряду — зависит от ширины сетки), дальше неделя листается стрелками под сеткой; страница
держится в URL как `?page=2`. Стрелки в шапке, как у фильмов, листают недели.

Источник — Shikimori API (`https://shikimori.io/api/graphql`), не HTML страницы
`/ongoings`: API не отдаёт CORS-заголовки, поэтому из браузера запрос невозможен, и данные
пишет серверный скрипт. Важное ограничение: у Shikimori нет расписания серий по дням, есть
только `nextEpisodeAt` — дата ближайшей серии онгоинга. Значит запись = одна серия
(аниме + день), и календарь наполняется по мере работы сервиса: прошлые недели видны только
за то, что скрапер уже увидел.

```bash
# только парсинг, ничего не записывается
npm run scrape:anime -- --dry-run

# парсинг + запись в PocketBase (коллекция должна существовать — миграция)
PB_EMAIL="admin@example.com" PB_PASSWORD="password" npm run scrape:anime -- --status ongoing

# дежурный режим: окно 7 дней назад и 21 вперёд, каждые 6 часов
PB_EMAIL="admin@example.com" PB_PASSWORD="password" npm run scrape:anime -- --watch --back 7 --forward 21 --interval 360
```

Флаги:

- `--status ongoing` — статус выборки (`ongoing`, `anons`, `released`), по умолчанию `ongoing`
- `--order popularity` — сортировка выборки, максимум 50 записей на запрос
- `--back N` / `--forward N` — окно дат в днях (7 и 21 по умолчанию)
- `--pages N` — сколько страниц онгоингов читать за проход (30 — это весь ongoing)
- `--delay MS` — пауза между запросами к GraphQL, по умолчанию 1200 (лимит Shikimori 5rps/90rpm)
- `--limit N` — максимум записей за проход
- `--interval N` и `--budget N` — дежурный режим: минуты между проходами и запросов за проход
- `--daily-budget N` — запросов GraphQL за сутки; при исчерпании скрипт ждёт полуночи по `TZ`
- `--dry-run` — вывод в консоль без записи
- `--backfill` — обновляет только поля карточки (описание, рейтинг, жанры, серии) и `kinopoiskId`
  во всех уже созданных записях аниме (проход по страницам ongoing, окно дат не важно)

Запись ищется по паре `shikimoriId` + `date`, поэтому один и тот же онгоинг не плодит дубли:
поля меняются, только если данные реально изменились.

Плитка аниме ведёт внутрь проекта так же, как плитка фильма — на страницу плеера `/watch`.
От Shikimori берутся только данные календаря: дата серии и постер; по ним строится ссылка.
Если у аниме известен `kinopoiskId` (номер из `externalLinks`, `kind == "kinopoisk"`, ссылка вида
`https://www.kinopoisk.ru/series/382731/` — скрапер вытаскивает его в поле `kinopoiskId`, миграция
`1730000320_updated_anime_releases_kinopoisk.js`, заполняется проходом `--backfill`), плитка ведёт
на `/watch?id=<kinopoiskId>`, где работают обычные источники: Alloha, Collaps, Kodik.
Если номера нет, плитка ведёт на `/watch?id=<shikimoriId>&type=anime` — там аниме ищет Kodik API
по `shikimori_id` или по названию записи (`kodikSearch` в `src/lib/shared/kodik.js`).

Важно: поиск Kodik работает только по токену из `.env` (`KODIK_TOKEN`). Публичный токен,
который парсится из скрипта плееров через `/api/kodik-token` (то же, что делает
`kodikwrapper.getPublicToken`), отвечает только `get-player`; на `search` он даёт 401 — проверено
запросом (`scripts/check-kodik-search.mjs`). Поэтому без токена в `.env` ищущая ветка всегда
показывает «нет токена». Параметр поиска называется ровно `title`: `keyword`, `name`, `q`,
`search` и `query` API отвечает 400 «Не указан хотя бы один параметр для поиска» — тоже
проверено запросом. Токен из личного кабинета kodikapi.com у этого проекта отвечал 401 на всех
методах, поэтому в `.env` стоит рабочий публичный токен того же API (из открытого репозитория
парсеров AnimeParsers); он не наш и может быть отозван — если перестанет отвечать, нужен свой.
После смены токена web-контейнер нужно перезапустить: его подставляет nginx.
Alloha отвечает только по номеру фильма в Kinopoisk, поэтому без `kinopoiskId` он помечен «нет id».

Карточка `/anime?id=<shikimoriId>` осталась: она нужна, когда найти плеер нечем, и с страницы
плеера есть ссылка на неё (с тем же днём календаря). Там постер, жанры, рейтинг, описание и даты
серий из календаря, плюс ссылка на Shikimori и на плеер, если `kinopoiskId` известен.
Ссылка на Shikimori в Kinopoisk есть примерно у трети онгоингов (на 27 октября — 106 записей
`anime_releases` из 481 с заполненным `kinopoiskId`).
Поля карточки (`description`, `score`, `genres`, `episodesTotal`, миграция
`1730000310_updated_anime_releases_card_fields.js`) пишет скрапер; уже созданные до миграции
записи заполняются один раз проходом `--backfill`.

### Календарь дорам (вкладка «Дорамы»)

Третья вкладка того же блока (коллекция `dorama_releases`, миграция
`pb_migrations/1730000400_created_dorama_releases.js`, применится при следующем запуске
PocketBase). Вкладка в URL: `?type=dorama`. Листается так же, как аниме: не больше 2 рядов
плиток, остальное — стрелками под сеткой (`?page=2`), стрелки в шапке листают недели.

Источник — страница списка `https://2.doramatv.red/list?sortType=DATE_CREATE`. Автоматическим
запросам этот домен отвечает «NOT FOUND», поэтому скрапер ходит на рабочее зеркало того же
сайта — `https://m.doramatv.one` (зеркало указано в шапке сайта; меняется через `DORAMATV_URL`
или `--base`). Из браузера запросы тоже не сделать: сайт не отдаёт CORS-заголовки, поэтому
данные пишет серверный скрипт, а вкладка читает их из PocketBase и подписывается на Realtime API.

Что берется из источника — только фактические данные плитки: id (`data-id`/`el_<id>`), slug,
название (из `alt` постера), ссылка на постер (`data-original`), подпись статуса и тип. Даты на
странице списка нет — там только порядок сортировки по дате добавления, поэтому дату берут с
карточки дорамы: блок `cr-frequency-details__item`, первое значение `dd.mm.yyyy` («Дата начала»).
Значит на новую дораму приходится два запроса: список (50 плиток) и карточка (1 дорама). Дату
пишут один раз — записям с датой карточку больше не читают, поэтому дежурный цикл стоит почти
ничего. Тексты описаний с сайта скрипт не читает и не пишет.

```bash
# только парсинг, ничего не записывается
npm run scrape:doramas -- --dry-run

# парсинг + запись в PocketBase (коллекция должна существовать — миграция)
PB_EMAIL="admin@example.com" PB_PASSWORD="password" npm run scrape:doramas -- --pages 2

# дежурный режим: 1 страница списка за цикл, каждые 15 минут
PB_EMAIL="admin@example.com" PB_PASSWORD="password" npm run scrape:doramas -- --watch --pages 1 --interval 900
```

Флаги:

- `--pages N` — сколько страниц списка читать за проход (по умолчанию 2, 50 плиток на страницу)
- `--delay MS` — пауза между запросами, по умолчанию 1200
- `--limit N` — максимум дорам за проход
- `--interval N` и `--budget N` — дежурный режим: минуты между проходами и запросов за проход
- `--daily-budget N` — запросов за сутки; при исчерпании скрипт ждёт полуночи
- `--base URL` / `DORAMATV_URL` — зеркало источника
- `--dry-run` — вывод в консоль без записи
- `--fill-ids` — заполняет `shikimoriId`, `kinopoiskId` и `matchNote` там, где их ещё нет: один
  запрос Shikimori на дораму по трём вариантам имени (см. ниже), только точное совпадение
  названия или единственный результат
- `--fill-only` — только этот шаг, страницу списка не читать
- `--shikimori-limit N` — записей без id за цикл (по умолчанию 25)
- `--shikimori-budget N` — запросов к Shikimori за цикл (по умолчанию 25)
- `--shikimori-daily N` — запросов к Shikimori за сутки (по умолчанию 60)
- `--original-limit N` — карточек за цикл, читаемых ради оригинального имени (по умолчанию 10);
  эти запросы считаются в общий бюджет запросов к источнику
- `--fill-kodik` — шаг id Kodik: поиск по названию (`title`) и запись `kodikId` там, где его ещё нет
- `--kodik-limit N` — дорам за цикл для этого шага (по умолчанию 20)
- `--kodik-daily N` — дорам за сутки (по умолчанию 60)
- `--kodik-delay N` — пауза между запросами Kodik, мс (по умолчанию 700)
- `KODIK_TOKEN` — токен, нужный шагу `--fill-kodik` (без него `search` отвечает 401)
- `SHIKIMORI_USER_AGENT` — названный пользовательский агент для Shikimori

Запись ищется по `doramatvId`, поэтому одна дорама не плодит дубли: дата появляется, когда
карточку читают впервые (или когда у записи её ещё нет).

Плитка дорамы ведёт на внутреннюю страницу плеера: `/watch?id=<doramatvId>&type=dorama`. Там
тот же блок плееров, что у фильмов, и краткая строка из фактических полей записи (тип, год,
статус). Тексты описаний с сайта на страницу не попадают — скрапер их не читает и не хранит.

Плееры привязаны к номеру материала в Kinopoisk, а такого номера у дорам в источнике нет.
Его приносит Shikimori, который считает дорамы обычными записями: скрапер ищет запись по
названию и берёт `kinopoiskId` из её `externalLinks` (шаг `--fill-ids`), и по этому номеру
работают Alloha и Collaps. Сам плеер на странице дорамы — Kodik, и у него два пути.
Первый — `get-player?id=<kodikId>`: скрапер (шаг `--fill-kodik`) находит дораму по названию и
пишет id собственной записи Kodik, вида `serial-77852`; по нему `get-player` отвечает и по
публичному токену плеера, то есть самой странице поиск не нужен. Второй путь — `get-player` по
`shikimoriId` (`kodikPlayerByShikimoriId`). `kodikSearch` остался последним запасным путём —
он требует токен из `.env`, потому что на `search` публичный токен отвечает 401.

Совпадение названия строгое и по трём вариантам имени: имя из плитки, «Оригинальное название»
из карточки (фактическое поле, скрипт читает карточку ради него) и имя без номера сезона
(«Тысячелетний господин 3» → «Тысячелетний господин»). Второй поиск по оригинальному имени
делается только если первый по имени источника ничего не дал. Принимается только точное
совпадение или единственный результат; как именно совпало — пишется в `matchNote`, близкий
вариант показывается на странице как подсказка, но не используется.

Покрытие по-прежнему низкое, и это честно: список источника смешивает сериалы с вебтунами, и
Shikimori знает эти работы как мангу/манхву под другими именами. Из 98 записей совпала одна —
«Левиафан» (Shikimori 59005, Kinopoisk 6264020): Kodik по этому id ответил плеером, а Collaps
по тому же номеру ответил 422, то есть источника там нет. Проверка 15 записей с оригинальными
именами (15 карточек, 30 запросов Shikimori) новых совпадений не дала: там, где Shikimori
находит работу, это другое произведение («Дом удобрений» → «Дом, мой дом», «Мой надежный муж»
→ «Зять»). Искать по разделу `mangas` смысла нет: Kodik играет только аниме-записи, по id
манхвы `get-player` отвечает `found=false` (проверено на двух id).

При этом дорамы играются и без Shikimori: Kodik знает их сам, по названию. Проверка 30 записей
без `shikimoriId` (один запрос на дораму, токен из `.env`): запись Kodik нашлась для 29 —
14 `foreign-serial`, 5 `foreign-movie`, 8 `anime-serial`, 2 `anime`. Поэтому шаг `--fill-kodik`
пишет `kodikId` там, где Shikimori молчит. Фильтр `types=dorama` не используется: API считает
его неверным типом («Неправильный тип»), дорамы лежат в `foreign-serial` и `foreign-movie`.

Поля `shikimoriId`, `kinopoiskId`, `originalTitle`, `matchNote`, `kodikId` и `kodikNote`
(миграции `1730000410`, `1730000420`, `1730000430` и `1730000440`) пишет только скрапер: правила PocketBase на создание и обновление
у коллекции `null`, из браузера запись не меняется.
Страница дорамы читает: если id в записи нет, она сама ищет название через прокси
`/api/shikimori/` (`src/lib/shared/shikimori.js`) и держит паузу 1200 мс между запросами —
Shikimori разрешает 5 запросов в секунду и 90 в минуту.

Постеры дорам отдаёт CDN источника `dr.one-way.work`: он принимает запрос только с referer
страницы самого зеркала (проверено: пустой referer и наш домен — 403, referer
`https://m.doramatv.one/` — 200), поэтому браузер напрямую картинки не грузит. В браузере
постеры идут через прокси nginx `/api/dorama-poster/`, который подставляет referer источника
и кэширует ответ сутки. В PocketBase хранится исходный адрес постера, путь прокси собирает
`src/lib/shared/doramaPoster.js` (список хостов там же, что и апстрим в `nginx.conf.template`).
